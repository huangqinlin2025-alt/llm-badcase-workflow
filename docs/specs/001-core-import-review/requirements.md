# SPEC-001：核心导入、判定与审核闭环

- 状态：已冻结
- 版本：1.0
- 日期：2026-09-06
- 对应范围：`ARC-001`、`DATA-001`、`IMP-001`、`MERGE-001`、`RULE-001`、`WECOM-001`、`REV-001`、`UI-001`、`QA-001`

## 目标

将当前静态 Demo 升级为可真实交互的单机服务：操作员提交一批评分文件，系统按显式业务键精确合并、筛选 badcase、持久化审核事实，并将结果幂等投影到机器人创建的固定企微大库和小库。

SQLite 是任务、候选、审核、幂等、外部投影和失败补偿的唯一事实源；企微表格是协作视图，不承担唯一状态或事务责任。

## 角色

| 角色 | 首期能力 |
| --- | --- |
| 操作员 | 提交导入批次，查看本人的导入结果、解析报告和候选 |
| 审核员 | 采纳或驳回待审核候选，填写采纳用途和审核备注 |
| 系统/机器人 | 解析、对齐、判定、持久化、企微投影、重试和对账 |
| 运维配置者 | 配置令牌、审核员白名单、固定企微文档/子表和规则版本 |

首期授权采用服务端令牌和审核员白名单；所有事件记录 `actor_id` 与 `project_id`，但不实现 SSO、完整 RBAC 或多租户管理。

## 业务范围

### 包含

1. 支持 CSV、TSV、简单 XLSX 的真实文件上传；支持符合白名单的 HTTPS 企微表格链接。
2. 同一导入批次支持多个来源文件，以 `case_id + side + evaluation_version` 精确合并。
3. 使用当前四类信号：绝对低分、人机分歧、机检 LLM 冲突、维度离群。
4. 使用 SQLite 保存导入、解析报告、候选、审核事件、投影状态、Outbox 和审计事件。
5. 候选自动投影至固定企微大库；审核采纳后回写大库并投影至固定企微小库。
6. 支持重复导入/重复审核的幂等处理、企微失败补偿和对账。
7. 现有静态页面改为调用真实 API；不再以 `data.js` 或 `pipeline_result.json` 作为业务状态源。

### 不包含

LangGraph、跨天流程 checkpoint、企业 SSO、完整 RBAC、模糊/向量/LLM 匹配、自动规则调参、硬伤/AB 劣势/软违规扩展规则、复杂 XLSX、多实例/高可用、消息队列、历史数据迁移。

## 输入契约

一个导入批次包含一个或多个来源文件。每个可参与精确合并的标准记录必须提供：

| 字段 | 规则 |
| --- | --- |
| `case_id` | 非空稳定业务 ID；禁止用行号自动补齐 |
| `side` | 非空；例如 `A` 或 `B`，由列或文件元数据明确提供 |
| `evaluation_version` | 非空；由请求元数据或文件中显式提供，禁止猜测 |
| 评分数据 | 至少一方存在有效数值评分；允许人工、LLM、机检覆盖不均 |

同一批次的合并键为 `case_id + side + evaluation_version`。同键中，人工/LLM/机检来自不同来源时可合并；同一来源对同一键的文本或分数冲突时不得覆盖，必须产出冲突报告。

仅接受 `.csv`、`.tsv`、`.xlsx`；`.xlsm` 在首期拒绝。上传和 URL 读取均须受服务端限制：格式、MIME、大小、行数、单元格长度、解压后大小和超时。企微链接仅限 HTTPS、允许的企微域名和可解析 `docid`，且机器人必须拥有读取权限。

## 判定规则

规则集名称为 `core-v1`，阈值固定为：

```json
{"low_dim":4,"low_overall":6.0,"disagree":1.5,"outlier_gap":2.0}
```

- 绝对低分：主评分方（优先 LLM，否则人工）任一维度 `<= 4`，或有效维度均分 `< 6.0`。
- 人机分歧：人工和 LLM 均分绝对差 `>= 1.5`。
- 机检 LLM 冲突：机检均分 `<= 6`，且 LLM 第一维 `>= 8`。
- 维度离群：某一维比同场景、同评分方、同维度均值低 `>= 2`。
- 严重度：至少三类信号为 `P0`；两类信号或包含人机分歧为 `P1`；其他为 `P2`。

缺失评分方的含义为 `unknown`，不代表规则未命中。每次候选必须保存 `rule_set_version`、阈值快照和可读证据。格式软违规、硬伤、AB 显著劣势不进入本规则集。

## 状态机

导入批次：

```text
RECEIVED → PARSED → ALIGNED → DECIDED → PROJECTING_BIG → PENDING_REVIEW
                                      ↘ PARTIAL_FAILURE
任意不可恢复校验失败 → FAILED
```

候选审核：

```text
PENDING_REVIEW → APPROVED → PROJECTING_SMALL → COMPLETED
PENDING_REVIEW → REJECTED
```

企微投影状态独立于业务状态：`PENDING`、`RUNNING`、`SUCCEEDED`、`RETRYABLE_FAILURE`、`UNKNOWN_RESULT`、`PERMANENT_FAILURE`。大库投影未成功的候选可被查看但不可审核；审核 API 返回投影未就绪错误，避免小库先于大库写入。

审核命令必须带候选版本。只有当前版本、当前状态为 `PENDING_REVIEW` 的命令可成功；重复或过期命令返回冲突，不覆盖既有结论。新导入不得将已采纳或驳回候选重置为待审核。

## 幂等与一致性

`candidate_key = case_id + side + evaluation_version + rule_set_version`；`content_hash` 覆盖参与判定的标准化内容。相同 `candidate_key` 且相同 `content_hash` 为无变化重放，不重复创建候选或企微行；内容变化仅更新自动生成字段，绝不覆盖审核人、审核备注或已终态审核结论。

SQLite 事务先写入业务事实和 Outbox，再由工作器执行企微投影。企微超时是 `UNKNOWN_RESULT`：必须先按稳定键查找/对账，再决定是否重发。不得使用从第 0 行覆盖的批量写入模式；不得以新建文档或新建任意子表作为错误恢复手段。

## 可验证验收结果

1. 同时上传人工、LLM、机检三份文件后，可按精确键合并并展示覆盖分布。
2. 主样例可生成与当前四类规则一致的候选、严重度和证据。
3. 同一合并键冲突时可定位文件、行、字段；冲突项不写企微。
4. 同一批次重复提交不会产生重复候选、重复大库行或重复小库行。
5. 采纳会持久化审核信息、更新大库并写入小库；驳回只更新大库。
6. 企微失败或服务重启后，待投影任务可重试和对账，页面不显示虚假成功。
7. 含 HTML/脚本内容的字段只按文本显示；客户端不能指定目标企微文档或执行命令。
