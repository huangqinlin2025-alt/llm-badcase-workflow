# ADR-001：SQLite 为事实源，企微双库为幂等协作投影

- 状态：接受
- 日期：2026-09-06

## 背景

现有 Demo 直接将判定结果写入企微表格，前端审核仅保存在浏览器内存，且写入从第 0 行开始，无法保证审核状态、重复导入和失败恢复的一致性。机器人又仅能写自身创建的文档，企微无法承担本地业务事务与可靠幂等的唯一事实责任。

## 决策

首期使用本地 SQLite 保存所有业务事实：导入批次、来源文件、标准化/对齐结果、候选、审核事件、稳定键、远端行定位、Outbox 和审计事件。企微大库和小库仅作为协作投影。所有外部写入必须由 SQLite 事务产生 Outbox，并由可重试、可对账的 Gateway 处理。

## 后果

优点：审核刷新不丢失；重复导入可去重；写入失败可恢复；可保留审计和版本；未来可迁移到 PostgreSQL 或由 LangGraph 编排而不重写领域逻辑。

代价：需要管理 SQLite 文件备份、迁移和单进程写入；企微与 SQLite 之间采用最终一致性，页面必须明确“待同步”状态。首期不支持多实例并发部署；未来扩展到多实例时迁移 PostgreSQL。

## 不采纳方案

1. 仅以企微表格为数据库：无法安全处理审核、幂等、事务和失败恢复。
2. 直接引入 LangGraph checkpoint 作为状态库：checkpoint 只解决编排恢复，不能替代业务审计与企微副作用幂等。
3. 前端本地保存审核状态：刷新即丢失，且无法形成可信审计。
